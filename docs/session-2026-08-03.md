## Méthode : mesurer la fiabilité AVANT de coder

Fiabilité par signature mesurée sur le corpus réel, comme cela avait été fait pour l'année :

| Champ | Fiabilité | Contenu |
|---|---|---|
| **Carrosserie** (`vehicule`) | **71 %** | 31 valeurs propres : Sedan, Hatchback, 4x4, SUV, Wagon/Kombi, Fourgon, Tracteur… |
| **Motorisation / version** (`type`) | **63 %** | cylindres + moteur ; la cylindrée (« 1.9 », « 3.0 ») n'est présente que sur 42 % |
| **Segment / classe** (`finition`) | **88 %** | classification marché : Lower/Upper Medium… |

La **cote** a été écartée. Les trois autres sont affichés en information **secondaire** (l'opérateur
confirme), lignes vides masquées.

## Ce qui est fait

### Phase A — Seed étendu (`00f67d0`)

Corpus ré-extrait avec les 3 colonnes supplémentaires ; `gen-vin-seed.py` enrichit chaque signature
de `carr` / `ver` / `seg`. Exemple réel :

```json
"SB1EA56L": {
  "mm": [["TOYOTA - AVENSIS KOMBI 03-06 >> AVENSIS '03", 4], …],
  "an": [[2005,2],[2006,2],[2007,1],[2008,1]],
  "carr": "Voit. Hatchback 5 p.", "ver": "AVENSIS 2.2 D-4D SOL", "seg": "Upper Medium"
}
```

Couverture sig8 : **carrosserie 100 %**, **version 100 %**, **segment 78,6 %**.
`vinSeed.json` : 1,65 Mo → **2,66 Mo**. **Benchmark inchangé à 78,1 %**, `wmiBase.ts` byte-identique.

### Phase B — Index + affichage (`c87d32d`)

- Table **`VinIndexInfo`** (migration `20260803155716_vin_index_info`), **15 439 lignes** importées
  (dédoublonnées sig8/sig6, seulement les entrées renseignées). Import **idempotent** vérifié.
- `chercher()` étendu ; lignes **Carrosserie** et **Motorisation** ajoutées après « Modèle »,
  **Segment** après « Zone WMI » — chacune rendue **uniquement si renseignée**.
- Hauteur de la fenêtre décodeur portée de **620 à 700** pour rester **sans scroll**.
- **24 tests verts**, tsc 0 erreur.

### Enrichissement en ligne (`b7511da`)

NHTSA `Body Class` → carrosserie, `Displacement (L)` + nombre de cylindres → motorisation.
**Écrit dans l'index sans écraser le seed.** **35 tests verts.**

## Deux décisions d'architecture prises ce jour

### 1. Partage de l'apprentissage entre postes → **reporté à la migration DB**

Question de l'utilisateur : *« OK également pour que tous les postes partagent ce qu'ils apprennent »*.

**Découverte** : la base est en **SQLite `userData/stca.db`**, donc **locale à chaque poste**.
Déplacer bêtement l'index sur un serveur central **casserait le hors-ligne**, qui est justement
l'atout du décodeur. Décision retenue : **plus tard, avec la migration DB** — quand l'app passera en
base serveur, le partage viendra naturellement, sans travail jetable. Consigné en mémoire.

### 2. 🔴 Faille MDI (ouverture sans authentification) → **parquée pour la finalisation**

L'utilisateur a relevé : *« C'est toi-même qui ouvre le décodeur sans la connexion d'utilisateur.
C'est possible ? »* — question juste. Réponse donnée : les tests passent par un **port de débogage**
(`--remote-debugging-port=9222`), une **porte de développeur** absente en production. Mais le fond
reste vrai : **les routes `#/mdi/<id>` sont rendues hors du guard d'auth**.

Décision de l'utilisateur :
> *« Nous allons le garder pour plus tard lorsque nous ferons les finalisations. Nous veillerons à ce
> que toutes les failles soient prises en compte. »*

→ Consigné en mémoire (architecture MDI) avec le correctif prévu, pour ne pas être oublié lors de la
passe de durcissement sécurité.
